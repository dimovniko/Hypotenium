# Техническое задание: сервис «Гипотениум» (Hypotenium)

Чат с ИИ-помощником для поиска по базе проведенных исследований.

> Рабочее название на момент написания ТЗ — «Researcher»; продукт переименован в «Гипотениум» (Hypotenium).

- **Версия:** 1.0 (MVP)
- **Дата:** 2026-08-03
- **Статус:** согласовано, к разработке

---

## 1. Суть продукта

Внутренний сервис, в котором пользователь в формате чата задает вопросы и гипотезы, а ИИ-помощник отвечает на основе базы исследований компании (отчеты, сырые данные, записи интервью). Каждый тезис ответа обязательно подкреплен ссылкой на конкретный артефакт и место в нем. Если релевантных данных нет — сервис прямо говорит об этом и не выдумывает.

Пользовательский путь:

1. Пользователь создает новый чат и пишет вопрос/гипотезу.
2. Сервис ищет по базе исследований и отвечает в понятном виде со ссылками на источники.
3. Пользователь доуточняет вопросами внутри того же чата, открывает источники в сайд-панели, при необходимости скачивает исходные файлы.

---

## 2. Роли и доступ

Две роли:

| Роль | Возможности |
|---|---|
| **Пользователь** | Чаты (создание, вопросы, уточнения), просмотр источников в сайд-панели, скачивание исходных файлов, шеринг своих чатов |
| **Админ** | Все возможности пользователя + раздел «Супердоступ» (управление исследованиями и пользователями) |

### 2.1 Регистрация и вход (упрощенная схема MVP)

- Регистрация «в лоб»: пользователь вводит email и пароль, аккаунт создается в статусе **«ожидает доступа»** и не может пользоваться сервисом.
- Админ во вкладке «Администрирование» видит новые аккаунты и выдает доступ (роль «Пользователь» или «Админ»).
- Вход по email + паролю. Сессия — JWT (access + refresh) или серверная сессия в cookie, на усмотрение разработчика.
- Пароли хранятся только в виде хэша (bcrypt/argon2).
- Первый админ создается сидом при развертывании (email/пароль из переменных окружения).
- Нормальная регистрация/авторизация (SSO и т.п.) — вне скоупа MVP, но код авторизации должен быть изолирован, чтобы ее было легко заменить.

## 3. Чаты

### 3.1 Базовое поведение

- Список чатов пользователя (сайдбар слева), кнопка «Новый чат».
- Сообщения: пользователь ↔ ассистент, ответы стримятся (постепенный вывод текста).
- Контекст диалога сохраняется: уточняющие вопросы работают внутри одного чата. Для уточняющих вопросов поисковый запрос переформулируется LLM с учетом истории (query rewriting), после чего выполняется новый поиск по базе.
- **Название чата генерируется LLM** автоматически после первого обмена сообщениями (как в Perplexity). Пользователь может переименовать чат вручную.
- Пользователь может удалить свой чат (с подтверждением). История хранится, пока пользователь сам не удалил чат.
- При удалении пользователя админом удаляются и все его чаты.

### 3.2 Шеринг чатов

- Владелец чата может расшарить его и отозвать шеринг (обе операции обязательны).
- Механика MVP: шеринг по ссылке. При включении генерируется ссылка с токеном; любой **авторизованный** пользователь сервиса по этой ссылке видит чат в режиме read-only. При отзыве шеринга токен инвалидируется, ссылка перестает работать.
- Нерасшаренный чат — личный: никто, кроме владельца, его не видит (включая админов).

### 3.3 Фильтр по датам

- Пользователь может текстом указать период («что мы выясняли про онбординг в 2024 году»). LLM извлекает период из вопроса, и он используется как **мягкий фильтр** (буст/приоритизация исследований по полю «дата проведения», не жесткое отсечение — пользователь может ошибаться в датах).

## 4. Ответы: поиск, цитирование, честность

### 4.1 Пайплайн ответа (RAG)

1. Вопрос пользователя (с учетом истории чата) → переформулировка в поисковый запрос.
2. Векторный поиск по чанкам всех исследований (top-k, порог релевантности). Опционально гибрид с полнотекстовым поиском Postgres — nice-to-have.
3. Найденные чанки с метаданными источников передаются в LLM вместе с системным промптом.
4. LLM формирует ответ с инлайн-цитатами.

### 4.2 Правила цитирования (жесткие требования)

- **Каждый содержательный тезис ответа обязан ссылаться на конкретный артефакт** инлайн-маркером вида `[1]`, `[2]`.
- Цитата указывает не просто на файл, а на **место** в нем:
  - PDF-отчет → номер страницы;
  - CSV → диапазон строк;
  - аудио/видео → таймкод (начало–конец фрагмента);
  - транскрипт → фрагмент текста с привязкой к таймкоду исходной записи.
- По клику на маркер `[1]` справа открывается **сайд-панель** с артефактом, промотанным/перемотанным к нужному месту (см. §5).
- **Если релевантных данных не найдено — сервис прямо отвечает, что в базе исследований по этому вопросу ничего нет.** Отвечать «из общих знаний» без источников запрещено промптом и постобработкой: ответ без единой цитаты допускается только в формате «ничего не найдено» или для служебных реплик (приветствие, уточнение вопроса).

### 4.3 Дедупликация внутри исследования

Если один и тот же вывод подтверждается и отчетом, и сырыми данными одного исследования, сервис должен **склеить его в один тезис с несколькими цитатами** (`…вывод… [1][2]`), а не выдавать два абзаца про одно и то же с разными источниками. Требование фиксируется в системном промпте; группировка чанков по исследованию при передаче в LLM должна этому способствовать (чанки в контексте группируются и помечаются: исследование → артефакт → место).

### 4.4 Технические сообщения об ошибках

Если API моделей недоступен — понятное сообщение пользователю («сервис временно недоступен, попробуйте позже»), без падения чата.

## 5. Сайд-панель просмотра источников

Открывается справа по клику на цитату `[n]`. Содержимое по типу артефакта:

| Тип | Просмотр | Позиционирование |
|---|---|---|
| PDF | Встроенный PDF-viewer | Скролл к нужной странице |
| CSV | Табличное представление | Скролл к нужным строкам, подсветка |
| Аудио | Плеер + транскрипт | Перемотка на таймкод, подсветка фрагмента транскрипта |
| Видео | Видеоплеер + транскрипт | Перемотка на таймкод (по аудиодорожке), подсветка фрагмента транскрипта |

- В панели всегда видно: название исследования, дата проведения, имя файла.
- Кнопка **«Скачать»** — отдает исходный файл (доступна всем ролям).
- Если артефакт или исследование удалены — вместо просмотра плашка **«Источник удален»** (старые чаты не ломаются, маркеры цитат остаются).

## 6. Супердоступ (только для админа)

Отдельный пункт в навигации, виден только админам. Две вкладки.

### 6.1 Вкладка «Исследования»

**Список исследований:** таблица (название, дата проведения, количество файлов, статус обработки, дата добавления), поиск по названию.

**Добавление исследования** — форма:

1. Название исследования (обязательно);
2. Дата проведения (обязательно);
3. Комментарий (необязательно);
4. Файлы-исходники (один и более, добавляются накопительно — по одному или пачками): PDF с отчетом, CSV с сырыми данными, аудио/видео с интервью. Лимит — **500 МБ на файл**.
5. **Комментарий к каждому файлу** (необязательно) — разметка «что внутри»: сегмент, респондент, волна опроса. Комментарий участвует в поиске: подмешивается в контекст эмбеддингов чанков файла и передается LLM вместе с источником. При изменении комментария эмбеддинги файла пересчитываются в фоне (без повторной транскрибации).

По кнопке **«Добавить исследование»** создается запись и запускается фоновая обработка (см. §7). Прогресс обработки виден в списке и в карточке исследования (статусы по каждому файлу).

**Карточка/редактирование исследования:**

- изменить название, дату, комментарий;
- добавить файлы (запускается обработка новых файлов) и удалить файлы;
- удалить исследование целиком (с подтверждением).

При удалении файла/исследования: файлы и их чанки удаляются из индекса и хранилища; цитаты в существующих чатах остаются, но при открытии показывают «Источник удален» (§5).

### 6.2 Вкладка «Администрирование»

Таблица пользователей: email, роль, статус (ожидает доступа / активен), дата регистрации. Действия:

- выдать доступ новому пользователю (назначить роль);
- изменить роль (Пользователь ↔ Админ);
- удалить пользователя (с подтверждением; удаляются и все его чаты).

Админ не может удалить сам себя или снять с себя роль админа, если он последний админ в системе.

## 7. Пайплайн обработки исследования (ingestion)

Запускается по кнопке «Добавить исследование» (и при добавлении файлов в существующее). Выполняется фоновым воркером, по каждому файлу независимо, со статусами: `загружен → в обработке → готов / ошибка` (при ошибке — понятное сообщение и кнопка «Повторить»).

Этапы по типам файлов:

**PDF (отчет):**
1. Извлечение текста постранично (для сканов без текстового слоя в MVP — статус «ошибка: нет текстового слоя»; OCR — вне скоупа).
2. Чанкинг с сохранением привязки к страницам.

**CSV (сырые данные):**
1. Парсинг (автоопределение разделителя и кодировки; поддержка UTF-8 и CP1251).
2. Чанкинг по группам строк с сохранением заголовка таблицы в каждом чанке и привязки к номерам строк.

**Аудио / Видео (интервью):**
1. Для видео — извлечение аудиодорожки (ffmpeg).
2. Транскрибация через API модели (см. §8) **с таймкодами по сегментам**. Языки: русский и английский (автоопределение).
3. Транскрипт сохраняется (сегменты: текст + start/end таймкоды).
4. Чанкинг транскрипта с сохранением таймкодов.

**Общий финал для всех типов:**
- Каждый чанк снабжается метаданными: `исследование, тип артефакта, файл, локатор (страница / строки / таймкод), язык`.
- Эмбеддинг каждого чанка через API (см. §8), запись в векторный индекс. В чанке сохраняется имя модели эмбеддинга.

Оригиналы файлов хранятся без изменений (для просмотра и скачивания).

## 8. Модели и интеграция с polza.ai

Все модели — внешние, по API. На старте — **polza.ai** (OpenAI-совместимый API). Три независимых слота:

| Слот | Назначение |
|---|---|
| `chat` | Ответы пользователю, переформулировка запросов, генерация названий чатов |
| `embedding` | Эмбеддинги чанков и поисковых запросов |
| `transcription` | Транскрибация аудио |

Требования:

- **Быстрое переключение моделей без пересборки.** Конфиг (YAML/JSON или таблица настроек в БД): для каждого слота — `base_url`, `api_key`, `model`. Конфиг перечитывается на лету (при каждом обращении или по file-watch) — рестарт и пересборка не требуются.
- Провайдер за OpenAI-совместимым интерфейсом — абстракция в коде, чтобы замена polza.ai на другой API была изменением конфига, а не кода.
- **Смена embedding-модели** делает существующий индекс несовместимым. В MVP: сервис хранит имя модели у каждого чанка; при несовпадении текущей модели с моделью индекса — предупреждение в админке и кнопка «Переиндексировать все» (фоновая переиндексация всех чанков без повторной транскрибации).
- Конкретные модели не фиксируются — подбираются при отладке.

## 9. Архитектура и стек

| Слой | Технология |
|---|---|
| Backend API | Python, FastAPI |
| Фоновые задачи | Воркер + очередь (Redis + arq/Celery) — транскрибация, эмбеддинги, переиндексация |
| Frontend | React (Next.js) |
| БД | PostgreSQL + расширение pgvector (HNSW-индекс) |
| Файлы | Локальный диск (volume) за S3-совместимым интерфейсом абстракции, чтобы позже переехать на S3/MinIO без переписывания |
| Медиа-обработка | ffmpeg (в образе воркера) |
| Развертывание | Docker Compose: `web`, `api`, `worker`, `postgres`, `redis` |

Обоснование масштаба: несколько тысяч исследований × сотни чанков — единицы миллионов векторов; pgvector с HNSW это держит, отдельная векторная БД не нужна.

## 10. Модель данных (черновик)

```
users:        id, email, password_hash, role (user|admin),
              status (pending|active), created_at

chats:        id, user_id (FK, cascade delete), title,
              share_token (nullable), created_at, updated_at

messages:     id, chat_id (FK, cascade delete), role (user|assistant),
              content, created_at

citations:    id, message_id (FK), ordinal (номер [n]),
              study_id, file_id (nullable после удаления источника),
              locator (jsonb: {page} | {row_from,row_to} | {t_start,t_end})

studies:      id, title, conducted_at (date), comment,
              created_by, created_at

files:        id, study_id (FK), kind (report_pdf|raw_csv|audio|video),
              original_name, storage_path, size_bytes, mime,
              status (uploaded|processing|ready|error), error_message

transcripts:  id, file_id (FK), language,
              segments (jsonb: [{text, t_start, t_end}])

chunks:       id, study_id, file_id (FK, cascade delete),
              content, locator (jsonb), language,
              embedding (vector), embedding_model
```

Примечание: `citations.study_id/file_id` не каскадируются при удалении источника — вместо этого файл помечается удаленным или FK обнуляется, чтобы в старых чатах работала плашка «Источник удален».

## 12. Интерфейс (MVP, без финального дизайна)

Дизайн будет предоставлен позже — на MVP аккуратная нейтральная верстка. Десктоп-first + адаптивность под мобильные.

Экраны:

1. **Вход / Регистрация** (+ экран «ожидайте выдачи доступа»).
2. **Главный экран чата:** сайдбар со списком чатов и кнопкой «Новый чат»; область диалога; поле ввода; инлайн-цитаты `[n]` в ответах; выезжающая справа сайд-панель источника.
3. **Супердоступ** (пункт в навигации только у админа): вкладки «Исследования» (список, форма добавления, карточка) и «Администрирование» (таблица пользователей).

---

## 13. Нефункциональные требования

- **Масштаб:** архитектура рассчитана на несколько тысяч исследований; на старте — десятки. Пагинация во всех списках.
- **Файлы:** до 500 МБ на файл; загрузка с прогресс-баром; медиа отдается со стримингом (HTTP Range) для перемотки по таймкодам.
- **Языки данных:** русский (основной) и английский — транскрибация и эмбеддинги должны поддерживать оба.
- **Язык интерфейса:** русский.
- **Секреты** (API-ключи, пароль первого админа) — только через переменные окружения / конфиг, не в коде.
- **Развертывание:** локально одной командой `docker compose up`.

---

## 14. Вне скоупа MVP

- SSO и «нормальная» регистрация (подтверждение email, восстановление пароля);
- роль «редактор исследований» без прав администрирования;
- OCR сканированных PDF;
- форматы DOCX/XLSX/PPTX, внешние доски (Miro/Figma);
- бэкапы и экспорт базы;
- жесткие фильтры поиска в UI (выбор исследований галочками и т.п.);
- финальный дизайн (будет загружен позже).

План работ после MVP — см. §16 «Вторая итерация».

## 15. Принятые решения (зафиксировано с заказчиком)

- Регистрация email+пароль, доступ выдает админ; первый админ — сидом.
- Ролей две, промежуточных нет.
- Удаление пользователя удаляет его чаты.
- Даты в вопросах — мягкий фильтр через LLM.
- Цитаты — инлайн `[n]` + сайд-панель с точным местом; просмотр в интерфейсе + кнопка «Скачать».
- Шеринг чатов с возможностью отзыва; нерасшаренное — личное.
- Названия чатов генерирует LLM; история живет до удаления пользователем.
- Лимит файла 500 МБ; из видео извлекается аудиодорожка, при цитировании видео открывается на таймкоде.
- Обработка (транскрибация, эмбеддинги) стартует по кнопке «Добавить исследование».
- Дубли «отчет + сырые данные» склеиваются в один тезис с двумя цитатами.
- Модели через polza.ai, переключение через конфиг на лету, без пересборки.
- Стек: FastAPI + Next.js + PostgreSQL/pgvector + Docker Compose.

## 16. Вторая итерация (план)

Сформировано по итогам эксплуатации MVP и тестов качества (прогон на реальном исследовании:
PDF-отчет «Менеджмент продуктов 2025» + 50-минутное аудио-интервью, 7 тестовых сценариев).

### 16.1 Качество поиска и ответов — приоритет 1

- **Гибридный поиск**: векторный + полнотекстовый (Postgres `tsvector`, конфигурации russian/english),
  слияние результатов через RRF (Reciprocal Rank Fusion).
  Мотивация: чисто семантический поиск пропускает фрагменты с точными терминами и разговорной
  речью с огрехами транскрибации — подтверждено тестом T7 (обсуждение эффекта ИИ на бизнес-метрики
  в подкасте не попадало в выдачу: Whisper услышал «ARR, P&L» как «в арки, пяй»).
- **Реранкер** (после гибрида, опционально): переранжирование top-50 → top-16 кросс-энкодером по API.
  Включать, если гибрид не закроет промахи.
- **Финальный подбор моделей** в `config/models.yaml` по результатам отладки. Требование к chat-модели:
  аккуратный перенос чисел из источников и честное «данных нет» — `gpt-4o-mini` этого не тянет
  (перевирал «1 220» до включения правила в промпт, додумывает при отсутствии данных).
- Подмешивать **комментарий исследования** (не только комментарий файла) в контекст эмбеддингов чанков.

### 16.2 Обработка сложных документов — по мере необходимости

- **VLM-парсинг страниц с инфографикой**: pypdf рвет числа, наложенные на диаграммы
  (в индексе «8% 10 2+ 1 п.п.» вместо «8%, 102 человека, +1 п.п.»). Решение — прогон таких страниц
  через мультимодальную модель. Дороже и медленнее, включать выборочно. Отложено осознанно.
- **OCR** сканированных PDF без текстового слоя (сейчас — статус «ошибка» с пояснением).

### 16.3 Авторизация и роли

- Нормальная регистрация: подтверждение email, восстановление пароля; при необходимости — SSO.
  Код авторизации в MVP изолирован, замена не затрагивает остальное.
- (кандидат) Роль «редактор исследований» — может управлять исследованиями, но не пользователями.

### 16.4 UX

- **Финальный дизайн** по макетам заказчика (макеты будут предоставлены), редизайн интерфейса.
- Шеринг чата конкретным пользователям (сейчас — по ссылке для всех авторизованных).
- (кандидат) Просмотр и ручная правка транскрипта админом — исправление имен, терминов
  и ошибок распознавания (влияет и на качество поиска).
- (кандидат) Жесткие фильтры поиска в UI: выбор исследований галочками, период дат.

### 16.5 Эксплуатация и масштаб

- HNSW-индекс в pgvector при росте базы до тысяч исследований (сейчас точный поиск, на текущих
  объемах быстрый).
- Бэкапы БД и файлового хранилища.
- Ускорение первого токена (сейчас 6–9 с): более быстрая/дешевая модель для переформулировки
  запроса, либо пропуск переформулировки для первого сообщения в чате.
- Новые форматы источников: DOCX/XLSX — по потребности.

### 16.6 Визуализация графиков по сырым данным (CSV)

Когда пользователь открывает цитату, ведущую на сырые данные, он должен видеть не только
табличный фрагмент с цифрами, но и **автоматически построенный график** по цитируемым данным.

Механика:

1. **Генерация спецификации графика.** LLM получает заголовок таблицы, цитируемый фрагмент
   и вопрос пользователя (контекст цитаты) и возвращает строгую JSON-спеку: тип графика
   (bar / line / pie / histogram), колонки X/Y, агрегация (count / sum / avg / доля),
   при необходимости — фильтр строк. Спека валидируется кодом: только существующие колонки
   и допустимые типы; произвольный код от LLM не исполняется.
2. **Расчет агрегатов на сервере по полному CSV**, а не только по процитированным строкам —
   чтобы распределения были честными (цитата лишь задает, что визуализировать).
   В подписи графика указывается N наблюдений.
3. **Рендер на фронте** легковесной библиотекой (Recharts / Chart.js) в сайд-панели
   над табличным фрагментом. Данные не покидают сервис — наружу уходит только спека в LLM.

Требования:

- график подписан: заголовок, оси, N, дата исследования;
- таблица остается доступна (переключатель или блок под графиком);
- graceful degradation: если по данным осмысленный график не строится (свободный текст,
  одна строка) — показывается только таблица, как сейчас, без ошибки;
- спека кэшируется на цитату — LLM не дергается при каждом открытии панели;
- (кандидат) те же графики инлайн в ответе ассистента, не только в сайд-панели.

### Порядок работ (рекомендация)

1. Гибридный поиск + повторный прогон тестовой батареи (сценарии T1–T7 сохранены).
2. Финальный подбор моделей, фиксация конфигурации.
3. Визуализация графиков по сырым данным (§16.6).
4. Нормальная авторизация.
5. Редизайн по макетам.
6. Остальное — по мере появления потребности.

## 17. Безопасность

Оценка по состоянию на конец этапа MVP (сервис работает локально).

### 17.1 Модель угроз: куда уходят данные

Все модели — внешние API, поэтому содержимое базы знаний по определению проходит
через провайдера моделей. Три потока наружу:

| Поток | Что уходит | Когда |
|---|---|---|
| Транскрибация | Аудиозаписи интервью целиком | При обработке файла |
| Эмбеддинги | Полный текст всех чанков (отчеты, CSV, транскрипты) | При индексации и переиндексации |
| Chat-модель | Вопросы пользователей + top-k найденных чанков + история чата | При каждом ответе |

Следствия:

- Провайдер видит весь контент. Гарантии нехранения/необучения — только договорные
  (политика провайдера, DPA), кодом не контролируются.
- **polza.ai — агрегатор**: данные проксируются дальше к upstream-провайдерам моделей.
  **GigaChat (Сбер)** — данные остаются в контуре Сбера в РФ, что предпочтительнее
  для комплаенса по ПД респондентов (152-ФЗ).
- Сценария «модель сама сливает данные» нет по построению: у модели в пайплайне нет
  инструментов, интернета и исполнения кода — только текст на входе и выходе.
  Prompt injection в загруженном документе может исказить ответ, но не «сделать» что-либо.
- Ответы модели рендерятся как текст (React экранирует HTML) — XSS через ответ закрыт.

Рекомендация для чувствительных интервью: обезличивать записи до загрузки
(имена, контакты респондентов) либо закрывать договором с провайдером. Радикальный
вариант — self-hosted модели (локальный Whisper, локальные эмбеддинги): архитектура
позволяет, провайдер меняется конфигом.

### 17.2 Что уже реализовано

- Пароли — bcrypt; сессии — JWT в httpOnly cookie (SameSite=Lax) + CORS только
  на origin фронтенда: кража сессии через JS и CSRF на мутации закрыты.
- Все админ-роуты за проверкой роли; аккаунты «ожидает доступа» не имеют доступа к данным.
- Чаты приватны (включая от админа); шеринг — невоспроизводимый токен (24 случайных байта),
  отзыв инвалидирует ссылку.
- SQL-инъекции закрыты ORM; path traversal при загрузке закрыт; идентификаторы файлов — UUID;
  скачивание/просмотр — только авторизованным активным пользователям.
- Секреты — только в переменных окружения.
- Загрузка исследований (и потенциальное «отравление» базы вредоносным текстом) — только у админов.

### 17.3 Чек-лист перед выкаткой за пределы localhost

1. Заменить дефолтные `JWT_SECRET` и пароль первого админа.
2. HTTPS через reverse proxy; cookie с флагом `Secure`.
3. Rate-limit на `/auth/login` (защита от брутфорса).
4. Для GigaChat: установить сертификаты НУЦ Минцифры в контейнер вместо `verify_ssl: false`
   (иначе уязвимость к MITM).
5. Решить вопрос шифрования файлов at rest (интервью с ПД лежат на диске в открытом виде).
6. Зафиксировать договоренности с провайдером моделей о нехранении/необучении (DPA).

### 17.4 Осознанные допущения MVP

- Прав доступа на уровне исследований нет: любой активный пользователь может получить
  через чат содержимое любого исследования (общая база знаний — по ТЗ).
- ffmpeg/pypdf парсят загруженные файлы — теоретический вектор через уязвимости парсеров;
  смягчено admin-only загрузкой и контейнерной изоляцией.

## 18. Инструменты (модули) чата

Реализовано как экспериментальный модуль: выключен по умолчанию, включается флагом
`tools.research_task: true` в `config/models.yaml` (перечитывается на лету).
Расширяемая система «инструментов»: модулей, которые встраиваются в диалог
и умеют вести собственные сценарии поверх обычного RAG-чата.

### 18.1 Архитектура

- Реестр `backend/app/tools/` — инструмент это класс с тремя точками входа:
  `check_trigger()` (предложение после RAG-ответа), `handle_action()` (клик по кнопке),
  `handle_message()` (сообщения, пока чат в режиме инструмента). Новый инструмент —
  новый класс + строчка в реестре.
- Триггеры детерминированные: условие срабатывания проверяет код, а не LLM
  (chat-модель ненадежна в выборе функций). LLM работает только внутри уже
  запущенного сценария.
- Кнопки — поле `actions` у сообщения ассистента (`[{id, label, data}]`), одноразовые:
  после клика обнуляются, клик фиксируется репликой пользователя. Эндпоинт
  `POST /chats/{id}/actions` отвечает тем же SSE-протоколом, что и обычное сообщение.
- Состояние сценария — `chats.mode` + `chats.tool_state` (JSONB): пока чат в режиме
  инструмента, сообщения идут в него; «отмена» или завершение возвращают режим `normal`.

### 18.2 Инструмент «Задача на исследование»

Сценарий: если по вопросу в базе нет информации (поиск пуст, ответ без ссылок на
источники или текст вида «ничего не найдено» — модель иногда ставит ссылки даже в
пустой ответ, ловим текстом), ассистент предлагает завести задачу на исследование
(кнопки «Да, создадим» / «Нет, спасибо»).

Брифинг — машина состояний, по одному вопросу за раз:

1. **Спрашиваем заказчика** (обязательные): продукт и контекст (+макеты),
   бизнес-задача, целевая аудитория, ключевые гипотезы, критерий успеха.
2. **Гипотезы валидируются по NN/g** (конкретность, проверяемость, действенность):
   плохо сформированная гипотеза не пропускается — ассистент объясняет, что не так,
   и предлагает формулировки (только утверждения, не вопросы); дальше только после
   подтверждения рабочего варианта. Ответ с отрицанием/критикой никогда не считается
   согласием (страховка кодом поверх LLM-экстрактора); отказ от предложенных
   формулировок возвращает к вопросу «сформулируйте своими словами».
2а. **Контроль конкретики ответов заказчика** (бизнес-задача, ЦА, критерий успеха):
   слишком общий ответ («хотим заработать», «все пользователи») вызывает один
   уточняющий вопрос; если заказчик настаивает — поле фиксируется как есть,
   но в саммери и в MD-файле появляется пометка для исследователя
   «⚠️ уточнить перед стартом» (брифуется сам заказчик, поэтому формулировка
   «уточнить с заказчиком» в диалоге была бы нелогичной).
   Методологическая часть генерируется строго по полям брифа (исходный вопрос
   чата в промпт не передается — чтобы смена продукта по ходу брифинга
   не протаскивала старый продукт в исследовательские вопросы).
3. **Опционально**: критичные требования к дизайну исследования (можно пропустить).
4. **Предлагает LLM, заказчик подтверждает**: главный исследовательский вопрос,
   исследовательские вопросы, методология, ожидаемые результаты и формат отчета,
   первый шаг (кнопка «Все подходит» или правки текстом).
5. **Саммери** всей задачи + кнопки «Создать задачу» / «Не создавать».

Держит контекст: пользователь в любой момент может уточнить ранний пункт
(«кстати, дополню по аудитории…») — extraction-шаг обновит нужное поле брифа.
Полнота брифа проверяется кодом, а не LLM: задача не создастся, пока обязательные
поля пусты.

Результат — MD-файл в папке `tasks/` (проброшена из контейнера в корень проекта):
все разделы брифа + метаданные (автор, чат, исходный вопрос) + секция «Связанные
исследования в базе» (векторный поиск по гипотезам и главному вопросу — топ-3
исследования, чтобы исследователь не дублировал уже сделанное).

Следующие шаги (по мере надобности): список задач в Супердоступе, статусы задач,
экспорт в трекер вместо/помимо MD-файла.
